# 把功能测试用例转成 YAML 自然语言用例

这个项目里，一条用例 = 一个 YAML 文件里的一项，只有**自然语言的目标（goal）**和**预期（expect）**。
没有选择器、没有坐标、没有站点脚本——`snapshot.js` 从真实 DOM 观测出候选元素，模型只在候选里选。

所以转写的本质是：**把「操作步骤 + 预期结果」翻译成「一个自然语言目标 + 若干可判定的断言」**，
而不是把步骤机械地映射成 API 调用。

读 [AGENTS.md](../../../AGENTS.md) 的分层与断言两节再动手。

## 一、先读源材料

各种格式先转成纯文本再读。用本 skill 的脚本（输出写文件而不是打屏——本机控制台是 cp936，中文打屏会变问号）：

```bash
uv run python .claude/skills/nl-case-author/scripts/read_source.py <源文件>
# -> 运行期写到 artifacts/case-source/<文件名>.txt（本机便签，不入库），然后读那个文件
```

| 格式 | 支持情况 |
|---|---|
| `.txt` `.md` `.csv` `.json` | 直接读 |
| `.xmind` | 直接读（zip 里的 `content.json` / `content.xml`） |
| `.docx` | 直接读（zip 里的 `word/document.xml`） |
| `.xlsx` | 需要 openpyxl，**用 uv 临时带上**：`uv run --with openpyxl python .claude/skills/nl-case-author/scripts/read_source.py 用例.xlsx` |
| `.xls` | 不支持，让用户另存为 `.xlsx` 或 CSV |
| 截图 / PDF | **让用户把用例手抄成文本**。不要看着图片猜断言——猜出来的断言会在评审时被发现是编的 |

源材料里通常有「用例编号 / 用例名称 / 前置条件 / 操作步骤 / 预期结果 / 优先级」这几列。
对应关系：编号 → `id`，名称 → `name`，操作步骤 → `goal`，预期结果 → `expect`，优先级 → `severity`。

**前置条件里凡是「已登录 / 已进入某页面」这类**，不要写进 goal：登录是框架的前置（`login:` 字段），
起始页面是 `url:` 字段。让 goal 从页面已经打开之后开始描述。

## 二、先查图谱：把功能实现搞清楚 ⭐

**源材料只告诉你「要点什么、该看到什么」，不告诉你「那个页面在哪、点下去会发生什么」。**
这些缺口靠猜写出来的 `url` 和 `goal` 会在执行时变成一条走不通的路径。所以**动手写 YAML 之前，
先转 [e9-graph-query](../e9-graph-query/SKILL.md) 查一遍 E9 的代码。**

> ⚠️ **本机没有 E9 源码**，只能走图谱 MCP。**禁止**用 Grep/Read/Glob 去找 E9 的实现——
> 那必然落空，而且会把「功能分析」这一步悄悄跳过。

### 主查前端，后端按需

| 想搞清楚什么 | 查哪张图 | 怎么查（配方见 [e9-graph-query](../e9-graph-query/SKILL.md) 第三节） |
|---|---|---|
| 这个功能**在哪个页面**、`url` 该写什么 | **`E9主干前端`** | 配方 A：找模块 `index.js` 里的 `<Route>` 路由表 |
| 界面上这个**按钮点下去做什么** | **`E9主干前端`** | 配方 B：`get_file_outline` + `get_code_snippet` 看 `formbtn.js` 一类动作函数 |
| 表单页 / 结果页的地址特征 | **`E9主干前端`** | 配方 C：找 URL 拼接函数（如 `Req.js` 的 `getMobxUrl`） |
| 这一步**之前**页面上必须先有什么 | **`E9主干前端`** | 配方 D：看模块结构与工具函数 |
| 这个按钮**最终打到哪个后端接口** | `E9主干`（Java） | 前端 URL 字面量 ↔ 后端 Route，**要手工桥接、且只能标为推测**（无跨图边） |

**默认只查前端图**。后端图（`E9主干`）是「想知道这条链路的服务端语义」时才用——
写 UI 用例要的是**页面、按钮、跳转**，三样都在前端图里。

### 查到的信息落到哪个字段

| 图谱查到的 | 写进用例 |
|---|---|
| 路由（`breadcrumbName` 中文名 ↔ `path` 英文段） | `url: "{{ base_url }}/wui/index.html#/main/workflow/listDoing"` |
| 按钮的语义与它的前置 | `goal` 里的步骤描述——**用界面上的中文名**（「提交」「待办事宜」），**不要写函数名** |
| 表单页 / 结果页的 URL 特征 | `expect` 的 `url_contains` |
| 页面上确定存在的文字（页签名、`breadcrumbName`） | `expect` 的 `text_contains` |
| 这一步**不该**出现的按钮/页签 | `expect` 的 `text_not_contains` / `element_absent` |

### 两条从图谱里读出来的、最容易写错的区别

1. **「保存」和「提交」是两条不同的链路。** 实测 `workflow/util/formbtn.js`：
   `doSave_nNew` 走 `src:"save"`、`doSubmitNoBack` 走 `src:"submit"`。
   源材料说「保存草稿」，goal 里就**不能**写成「提交」——那是另一个动作，
   会真的把流程推到下一个节点、产生真数据。
2. **门户壳不能互换。** 员工工作台是 `/wui/index.html`，后端引擎是 `/wui/engine.html`。
   把引擎的路由打进 `index.html` 只会渲染出门户首页——**用例会「打开成功」但一元素都没有**。
   `cases/e9/workflow_design.yaml` 开头记着这个坑。

### 图谱查不到什么（**别指望它替代 DOM 观测**）

- **UI 元素定位（id / xpath / 选择器）图谱里一个都没有**——HTML 只有 File + Module 节点，无 DOM/ID/onclick。
  所以图谱**替代不了** `snapshot.js` 的真实 DOM 观测，**不要试图从图里抄选择器**。
- **匿名事件 handler / 内联箭头回调不建节点**——「点完这个按钮之后具体做什么」的链条**在这里断掉**。
  这段只能靠 API 文档或直接在界面上试（配合 [nl-case-run](../nl-case-run/SKILL.md) 实跑）。
- 前端图只覆盖 4 个主目录（约 **80%** 的 js/ts）。查不到时**说「可能落在未覆盖区」，不要断言「不存在」**。

**查完要落到用例字段上才算数**——把图谱结论抄进对话、却没改进 `url` / `goal` / `expect`，
等于没查。交付时（见第八节）说明哪几个字段是查图谱定的。

## 三、写进哪个文件

默认落在 `cases/e9/`。一个**模块**一个文件（例如 `workflow_add.yaml`、`doc_search.yaml`），
文件里可以放多条同模块的用例。文件名用小写加下划线。

`cases/demo/` 放的是公开网站上跑、不需要 E9 环境的演示用例——功能用例不要放这里。

`id` 全局唯一，推荐 `<模块>-<动作>` 形式（`e9-workflow-add-bym`）。
重复 id 会在加载期直接报错，不会静默覆盖。

## 四、YAML 结构

```yaml
version: 1

# defaults 里的键会被每条用例继承，用例内的同名键覆盖它。
defaults:
  login: employee1          # employee1~5 / admin / none
  epic: E9-UI自动化
  feature: 流程管理
  severity: critical
  timeout_s: 420
  max_steps: 30

cases:
  - id: e9-workflow-add-bym
    name: 新建 BYM专用测试 流程并提交      # 会同时成为 Allure 的 story 与 title
    tags: [e9, workflow, smoke]
    url: "{{ base_url }}/wui/index.html#/main/workflow/add"
    goal: |
      用自然语言写清楚"做什么"。多步骤用编号列出来，每步一句话。
      提交成功后该表单页会自动关闭，回到新建流程的列表页；此时停止。
    expect_mode: and
    expect:
      - type: ai
        desc: 已回到流程名称列表页
        claim: 页面上显示的是新建流程的流程名称列表
      - type: text_not_contains
        value: "流转设定"
```

### 可用字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | 全局唯一 |
| `name` | ✅ | 中文用例名，Allure 里直接展示 |
| `url` | ✅ | 起始地址。E9 用 `{{ base_url }}/...`，**不要写真实内网地址** |
| `goal` | ✅ | 自然语言目标，上限 2000 字 |
| `expect` | ✅ | 非空断言列表 |
| `login` | | `employee1`~`employee5` / `admin` / `none`（默认 none） |
| `epic` `feature` `severity` `tags` | | Allure 分组；severity ∈ blocker/critical/normal/minor/trivial |
| `expect_mode` | | `and` / `or` / `min_pass`，**逐用例决定**，见下 |
| `min_pass` | | 仅 `expect_mode: min_pass` 时需要，落在 1~断言条数之间 |
| `threshold` | | 用例级语义断言阈值；不写就用全局默认 0.75 |
| `timeout_s` `max_steps` | | 执行预算，默认 300s / 60 步 |
| `reruns` | | 用例级重跑次数。设计上就该失败的负向用例设 `0` |
| `setup` | | **命名前置**：这条用例动手之前，环境里必须先存在什么。取值见下 |

字段名写错**会在加载期报错**，不会静默忽略——这是刻意的，静默忽略会让整条断言悄悄失效。

### `setup:` —— 一条用例只有一个登录身份，前置得靠接口备

**这是本项目最容易写错、也最容易漏的一处。** `runner` 在起浏览器之前注入一次 cookie，
**一条 UI 用例自始至终只有一个账号**；而源功能用例的前置常常是
「人员01 建 → 人员02/03 会签 → 人员04/05 审批 → 人员06 归档」这种跨人链条——
那段链条在 UI 用例里**表达不了**。所以它走接口、在 fixture 里做掉，用例只用名字声明：

⚠️ **上面那条是源用例的链路，不是本环境一定有 6 个账号。** 落到哪几个人身上由
环境决定，映射收敛在 `e9_setup.ROLE_*`。实测目标环境上只有 5 个账号，
归档那一角由人员05 兼（见 `e9_setup.ROLE_ARCHIVER` 的注释）——**写用例时不要
假设「人员06」存在**，也不要在 goal 里写死人数。

```yaml
  - id: e9-wf-submit-tc03
    login: employee2          # UI 只做人员02 这一次的动作
    setup: wf-approval2       # 环境里先备好：R1 已到「审批2」，人员02/03 有待办
    url: "{{ base_url }}/wui/index.html#/main/workflow/listDoing"
```

已登记的名字（见 `framework/e9_setup.py` 的 `SETUPS`）：

| `setup` | 前置是什么 |
|---|---|
| `none`（默认）| 没有前置，用例从"新建流程"这一步自己开始 |
| `wf-approval2` | R1 已到「审批2」会签节点，人员02、人员03 有待办 |
| `wf-approval3` | R1 已到「审批3」非会签节点（审批2 两人都已提交） |
| `wf-archived` | R1 已走完全流程、停在归档节点 |

三条规矩：

- **`goal` 只从这个节点的操作者登录之后开始描述。** 前置里发生过什么，goal 不要重复写——
  它没发生在这个 UI 会话里。要说明就在注释里说明。
- **跨人流转那段由接口走通，不是 UI 走通的。** 交付时要如实讲（见第八节），
  否则用户会以为 UI 真的验证了那条链路。
- **别自己造名字。** 需要新前置就往 `e9_setup.SETUPS` 里加配方，
  加载期不认得的 `setup` 值会在执行时报错（并列出可用的名字）。

**流程实例的名字用 `{{ wf_request_name }}`，不要写死。** 它在收集期由 loader 逐用例
生成（含 `run_id` 和用例 id），保证同一轮里每条用例各建各的实例——
写死的名字会让"在列表里找到刚建的那条"变成撞运气。前置 fixture 与 `goal`
用的是同一个值，两边都对得上。

## 五、写 goal：把步骤翻译成意图

goal 是给模型看的，不是给解析器看的。三条规则：

1. **写"要达成什么"，不写"点哪个坐标"**。`点击「BYM专用测试」` 是对的；
   `点击 #ecid-29384` 是错的（ecid 里是随机数，下次就变）。
2. **每个动作点到具体的元素名字**。模型靠名字在候选表里认元素，含糊的描述会让它选错。
3. **结尾明确"什么时候停"**。不写终点，模型不知道何时该选 `DONE`。

### 两个必须知道的行为事实

它们是实测出来的，不写进 goal 就会踩：

- **断言只对【终局页面】求值。** 中间步骤做过什么，终局断言看不见。
  所以**最后一步必须承载全部证据**：要校验某个输入框的值，就让那个页面成为最后一站
  （见 `cases/demo/weaver_site_tour.yaml` 为什么把案例页放在最后一站）。
- **agent 没有"后退"。** 路径只能前进。站点内换页要用页面上的导航，不能指望浏览器历史。

### 写 goal 时常见的坑

| 坑 | 表现 | 怎么办 |
|---|---|---|
| 元素在屏幕外 | 模型看不到该元素，于是跳过它 | 元素必须落在视口内才会成为候选。让 goal 明确写"向下滚动，找到 X"，或把目标拆成两步 |
| 异步加载 | 点完后页面还是空壳，模型以为没结果 | goal 里写"结果要等一下才出来，如果还没出现就先等待" |
| 目标名有随机数 | 每次都不一样 | 用稳定文案定位（`title` 属性、标签文字），避开 id/ecid |
| CJK 字间空格 | 界面上是「提 交」不是「提交」 | 别在 goal 里逐字抠字面量；让模型按语义找，断言侧用 `text_contains` 时也要注意 |
| **字段的可访问名是无关内容** | 文本助手判定"goal 要的值不在这个字段上"，返回 `{"text": null}`，或从 goal 的多个可填值里挑错一个 | 见下 |

**关于"字段名是无关内容"这条，值得单独说清楚**（实测，2026-09）：百度首页那个输入框的
可访问名来自 placeholder，内容是**当天的热搜词**——一条与搜索毫无关系的新闻标题。
于是 goal 说"在搜索框里输入泛微网络"，模型只能落在它身上（它是唯一可见的 textbox），
而文本助手看到字段名是新闻标题，判定值不匹配：

- 同一输入连测两次都返回 `null`；
- 把字段名换成正常占位符（"请输入搜索关键词"），连测两次都正确返回「泛微网络」；
- 在 goal 里额外说明"忽略那段占位文字"**也没用**，仍返回 `null`；
- goal 里只有一个可填值时，结果在 `null` 和正确值之间**摇摆**（1/2）。

这是可复现的确定性阻塞，不是抖动。**遇到就换路径**——换个起点 URL、换一条不经过该字段的
路线，或换一个字段名与用途对得上的站点。不要靠调措辞去绕，也不要为它放宽断言。

推论：**一条 goal 里尽量只留一个待填值。** goal 里有多个 `TYPE_TEXT` 目标时，
字段名不明确的那些会被填错（实测：该填「泛微网络」的框被填进了 goal 里另一个值「制造」）。

## 六、写 expect：断言的两级边界

**执行期**用 Jev 的 `choice` 概率做连续决策——那是模型的事，不用你写。
**终局**必须是 pytest 的确定性 `assert`。语义性预期由 Jev 的 `noul` 给 0–1 的**证据**，
**阈值比较与判定留在代码里**——不允许"问模型通过了吗"。

### 断言类型

| type | 必填 | 判据 |
|---|---|---|
| `ai` | `claim` | 语义断言。`noul ≥ threshold` 才算通过。**写正面、原子的事实描述** |
| `url_contains` / `url_equals` | `value` | URL 包含 / 等于（`url_equals` 可加 `ignore_query: true`） |
| `text_contains` / `text_not_contains` | `value` | 页面可见文本包含 / 不包含。`text_contains` 可加 `count: N` 要求至少出现 N 次 |
| `element_exists` / `element_absent` | `label` | 按可操作元素的 label 找得到 / 找不到。可加 `exact: true`、`role: button` |
| `element_value` | `label` + `equals` 或 `contains` | 校验元素当前的值 |
| `element_count` | `label_contains` + `equals`/`min`/`max` | 匹配某子串的元素个数 |
| `element_enabled` | `label` | 元素存在且未被禁用 |

### 选型原则：**先找确定性信号，找不到才用 `ai`**

确定性断言能表达就别用 `ai`——它免费、不抖、失败原因一眼可见。
只有当预期本身是语义判断（"页面上显示的是不是 XX 列表"）时才用 `ai`。

### 把预期写成"原子、正向"

实测：同一事实，否定式表述只能拿到约 **0.47**，正面陈述能到 **0.9+**。

```yaml
# ❌ 否定式，实测 0.47 —— 会失败
- type: ai
  claim: 表单页已经关闭，当前不在新建流程页面上

# ✅ 正面陈述同一件事，实测 0.9+
- type: ai
  claim: 页面上显示的是新建流程的流程名称列表
```

### 三条会拉低 `ai` 分的写法（都是量出来的，别踩）

| 写法 | 实测 noul | 怎么改 |
|---|---|---|
| **否定式**："已经关闭／不在…上" | 0.47 | 正面陈述同一事实 |
| **页面身份**："当前页面是该流程的流转设置界面"、"流程设置是当前选中的页签" | **0.10 / 0.24 / 0.40** | 改说**页面上看得见的具体东西**："页面上有「图形编辑」页签" → **0.98** |
| **复合句**：把两件事用「并且」串起来 | 0.54 | 拆成两条断言，每条一个事实 |

**为什么"页面身份"判不出来**：`流转设置` 只是四个并列页签之一，选没选中从页面正文里看不出来；
而"页面上有没有这个页签/按钮"是可核的。**修法是把话说成看得见的事，不是把阈值往下调**——
调阈值是把尺子改短。

> 实测闭环（2026-09-30，TC06）：同一件事连着量了三次——

> 中间那次掉到 0.08 **不是措辞问题**：那条必填提示是浮层 tooltip，
> **根本没进"页面可见文本"**——见下。

### 先确认那件事**看得到**，再决定怎么断言

`ai` 与 `text_contains` 都只看**页面可见文本**。**看得见但没进文本的东西断不了**：

- **浮层 tooltip**（E9 的必填校验提示实测就是）：截图里明明在，页面文本里一个字都没有；
- 输入框里**填了什么**（`value` 不在正文里，要用 `element_value`）；
- 被列表**在数据层截断**的标题。

所以一条断言反复调措辞都上不去时，**先回去看它要断的东西到底在不在页面文本里**——
不在就换一条能看到的信号，别继续改措辞（改到天亮也没用）。

### `expect_mode` 逐用例决定，没有全局默认

- `and` —— 全部通过才算通过。默认选它，但**确认每条断言都真的必要**：
  一条弱断言会把整条用例拖成假失败。
- `or` —— 任一通过即可。用于"两种正确结果都算对"的场景。
- `min_pass` + `min_pass: N` —— 至少 N 条通过。用于多条弱证据互补的场景。

## 八、交付时说什么

告诉用户：

1. 转出了几条用例、落在哪个文件；
2. **哪些字段是查图谱定的**（`url` 的路由、`goal` 里的按钮语义、`expect` 里的页签/URL 特征），
   以及**哪些是图谱查不到、只能靠试的**（元素定位、匿名 handler 的行为）——
   让用户知道确定性到什么程度；
3. **哪几条断言是你替用户做的判断**（尤其是 `ai` 的 claim 措辞和 `expect_mode`）——
   这些是需要用户确认的业务语义，不是格式转换；
4. 源材料里**没能转过来的部分**和原因（例如"前置条件依赖另一条用例的中间状态，
   而 agent 没有后退动作，这条路径走不通"）。

源材料里读不懂或自相矛盾的地方，**回头问用户**，不要自己补一个看起来合理的断言。
编出来的断言会在执行时变成一条永远失败或永远通过的用例，比缺一条用例更糟。
